
## Java And Bukkit

- Target Java 21 and use modern idioms when compatible.
- Assume Lombok is available; prefer it where appropriate.
- Use records for suitable data holders.
- Prefer loops; use streams only in infrequent paths when they significantly simplify code.
- Mark changed Java lines with // Codex start - <description> and // Codex end.
- Avoid singletons and Main.getInstance() patterns.
- Compare strings as variable.equals("literal").
- Always use ==/!= when API, registry, or lifecycle guarantees canonical identity; use equals() for independently created value objects.
- Use imports instead of fully qualified class names unless simple names collide. In that collision case only, a local variable may use var to avoid repeating the fully qualified name when its initializer makes the type fully obvious and readability is unchanged.
- Type variables by interfaces, such as List<String> instead of ArrayList<String>.
- Use EnumMap/EnumSet for enum keys and fastutil primitive collections for primitive keys.
- Store repeated non-trivial computations in local variables; simple field/record accessors need no local.
- Read configuration once into typed objects; use ConfigurationSection instead of repeated dotted lookups.
- Do not add redundant getCommand(...) null checks; do not call setTabCompleter(...) if the command executor and tab completer are the same object.
- Preserve isEmpty() before get() in hot collection paths; it can avoid hash/bucket work.
- Judge O(n) structures by real cardinality; for small sets they may beat O(1) structures.
- For connected-player session maps cleared on quit, use IdentityHashMap or fastutil collections with reference-identity semantics if the identity of keys from Player#getName() or Player#getUniqueId() is stable and every operation on a player's entry uses the same key instance from that player's object during the current session. If lookups require independently created keys that are equal by value, use a collection with equals() semantics.
- Async Bukkit reads and packet/message/sound/particle sends are allowed; keep world/entity mutation synchronous.
- Create custom inventories with a custom InventoryHolder.
- Use ItemStack#isEmpty() and Block#isAir() directly without extra wrappers.
- Don't use unnecessary try-catch blocks, .stream, and the like in .class files and methods. I also recommend that, before advocating for “optimized” uses of methods or getters, you compare them against a variety of options using JMH testing to measure performance with 100% accuracy.
- We recommend that you start by comparing the entire .class file, and only then begin writing code—make sure the .class file isn't overly complicated and is as simple as possible (as needed).
- Follow OOP best practices, especially the Single Responsibility Principle (SRP), encapsulation, and high cohesion.
- Before refactoring, analyze the entire class and determine whether it contains unnecessary responsibilities, nested types, duplicated logic, or excessive complexity.
- Keep configuration records as simple data holders. Do not mix configuration data with loading, parsing, business logic, or unrelated functionality.
- Avoid cluttering configuration classes with numerous nested records or classes. Prefer separate top-level records when configuration groups are sufficiently large or independently meaningful.
- Keep small nested types when they genuinely improve cohesion and readability. Do not extract classes solely to reduce line count.
- Prefer simplifying existing code over introducing unnecessary abstractions, interfaces, services, or helper classes.
- Each class should have a clear responsibility, and every abstraction should have a practical purpose.
- When you make a config configuration, we advise you not to make the following errors: config.getstring ("section.string"); each section must be declared in the ConfigurationSection variable even if sections of pieces 10-15, da?
- In Java, there is a very important variant of java.util.concurrent.TimeUnit — it might seem like, why are we adding this java.util.concurrent part if we can just import it, this is very silly and pointless, da? java.util.concurrent.TimeUnit — example.
- We advise against parsing patterns at runtime—as well as performing other costly operations—within loops or methods.
- We advise against performing the following actions within loops (`for` loops): Input/Output (I/O) operations, resource-intensive Bukkit API methods, operations on large collections, and the creation of tasks or schedulers.
- There is no need to implement "foolproofing" at all.
